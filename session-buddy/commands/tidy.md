# /tidy — 整理工作区

把当前工作区里散落的任务产物收纳进 `buddy/` 体系。按以下步骤执行：

## 1. 盘点

列出工作区根目录的全部内容（跳过 `.zcode`、`.git`、`node_modules`、隐藏文件和 `buddy/` 自身）。对每个条目判断它属于哪一类：

- **项目自身的文件**（源代码、配置、依赖声明等）——保持原位；
- **任务产物**（报告、生成的文档、导出的数据、演示页面、一次性脚本、图片等，通常修改时间较新且与项目本身无关）——待归档；
- **无法判断的**——列出来向用户确认。

## 2. 查引用

在提出搬动方案之前，先查清每个"待归档"文件有没有被别的文件引用：在工作区其他文本文件里搜索它的文件名和常见的相对路径写法（跳过 `.git`、`node_modules`、`.zcode` 和二进制文件；markdown 链接、HTML 的 `src`/`href`、脚本里的 `open(...)`、`read_csv(...)`、`fs.readFileSync(...)`、bat/ps1 里的路径等都要查）。把结果分成三类：

- **同去**：引用方本身也在本次归档的同一组里，搬完后相对引用依然成立 → 一起搬，不用改；
- **改引用**：引用方本身也是待归档的产物文件，明确写着旧路径 → 搬完后把引用方里的路径更新成新路径；
- **留原地**：被项目源码、配置或看不懂的文件引用，或拿不准 → 这个文件留在原地，在方案里注明原因。

## 3. 分组方案

按主题和修改时间把待归档的文件分成若干组，每组对应一个 `buddy/<YYYY-MM-DD>-<主题>/` 文件夹（日期取文件的修改时间，主题用中文概括）。同一主题的旧文件即使日期不同也可并入同一组。

**先把方案展示给用户**：每组列出"文件夹名 → 包含的文件 → 一句话说明"；有外部引用的文件单独标注处理方式（同去 / 改引用 / 留原地及原因）。得到确认后再动手，不要不问就搬。

## 4. 执行

- 创建文件夹并移动文件（用文件工具移动，保留原内容）；
- 按步骤 2 的结论更新引用：只允许修改"归档产物"文件里的引用路径，绝不修改项目源码；
- 同组内互相引用的相对路径，搬完后抽查一遍确认仍然成立；
- 每个文件夹写一份 `README.md`：任务说明、文件清单（文件 / 说明 / 怎么打开）；
- 更新 `buddy/INDEX.md`：新条目放最上面；若已存在则合并，绝不覆盖。

## 5. 报告

完成后向用户汇报：

- 移动前后的对照表、每个文件夹的一句话说明；
- 引用处理明细：改了哪些引用（旧路径 → 新路径）、哪些文件因为被引用而留在原地；
- 哪些文件保持原位。

## 规则

- 绝不删除任何文件，只移动和新建；
- 不确定用途的文件保持原位并询问；
- 拿不准的引用一律按"留原地"处理，宁可少搬；
- 用户明确指定位置的文件不动；
- 深层目录里的既有内容不要翻动，本次只整理根目录的散落文件。
